# Rust Port Contract

## Objective

Replace every non-UI implementation with Rust while preserving the product's
supported behaviour and public API. The existing TypeScript/React UI remains the
product interface and continues to call compatible REST endpoints.

Document processing is the first migration phase. Later phases include the remaining
Java server surface, the Python AI engine, non-UI Tauri host responsibilities, and
build/deployment wiring. Phase order does not narrow the terminal scope.

The current product supports browser, self-hosted server, and desktop delivery;

The generated frontend contract currently exposes 87 document-tool endpoints. The

The deployment images and source also rely on native processing tools including

Their final role is governed by the external-dependency scope decision below.

As of the current checkpoint, the additive Rust processing service implements the

and tests remain explicitly available as a compatibility oracle.

The versioned cross-surface inventory, including AI routes, desktop commands, and data

## Preserved Product Contract

Until a human explicitly approves a breaking release, the Rust system must preserve:

- every supported PDF operation and its observable result;
- the documented REST API routes, request handling, status codes, response headers,
  and response payloads;
- core, proprietary, SaaS, and desktop product surfaces;
- authentication, authorization, session, audit, billing, storage, and tenant
  isolation behaviour;
- document lifecycle, pipeline, background-processing, and AI-engine workflows;
- browser, desktop, self-hosted, and container deployment paths; and
- localisation, accessibility, and existing user data compatibility.

The current application is the behavioural oracle while it remains in the repository.
The migration must capture executable contract tests and deterministic document
fixtures before the matching implementation is removed.

## Migration Rules

1. Freeze an exact route and capability manifest from the current implementation.
2. Add Rust implementations behind contract tests; do not use an untested route count
   as proof of compatibility.
3. Move one complete processing slice at a time: API contract, authorization,
   document operation, persistence, observability, and browser-UI compatibility.
4. Compare Rust outputs with golden documents and with the legacy service where output
   is deterministic.
5. Do not delete a legacy component until its complete replacement passes the relevant
   unit, integration, end-to-end, platform, security, and performance proof.
6. Remove a Java processing path only after its Rust replacement passes the relevant
   migration matrix. Keep the browser UI in place; do not treat it as a Rust-port
   deliverable.

## Accepted Scope

Decision 0010 records the accepted terminal scope. Decisions 0008 and 0009 are
retained as earlier scope-analysis and initial-phase records.

- The existing browser UI stays in TypeScript/React.
- The Rust target is every non-UI runtime surface: Java server code, Python engine,
  non-UI Tauri host responsibilities, and required build/deployment integration.
- Java document processing is the first implementation phase, not the completion
  boundary.
- Public HTTP contracts remain backward compatible during a rolling migration.
- Existing native processors may remain behind explicit Rust adapters where required
  for compatible behaviour.
- The AI engine runtime has moved to Rust after its HTTP contract gate; Python
  remains an explicit oracle while deployment credentials and external storage
  are verified. The Tauri host now has a bounded opt-in Rust-launcher parity
  path with parent-lifecycle enforcement and fresh-install settings initialization,
  while upgrade-template migration, production sidecar/PDFium packaging,
  cross-platform bundle proof, and removal of the Java default remain a later
  cutover phase.

## Completion Evidence

The port is complete only when the following evidence exists:

- a baseline-to-Rust capability and route manifest with no unapproved gaps;
- contract, golden-document, integration, end-to-end, platform, performance, and
  security proof for each migrated surface;
- successful deployment and upgrade testing for each supported flavour; and
- an auditable source and runtime inventory showing that no unapproved Java or Python
  runtime dependency remains, while documenting the intentionally retained UI and
  approved native-tool adapters.
